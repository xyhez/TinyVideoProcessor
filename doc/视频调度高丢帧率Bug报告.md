# 视频调度高丢帧率 Bug 报告

## 1. 基本信息

| 字段 | 内容 |
|---|---|
| 问题标题 | 原始帧率预览时调度丢帧率异常偏高 |
| 发现日期 | 2026-07-18 |
| 当前分支 | `dev_ui_refactor` |
| 问题状态 | 代码已修复并通过静态检查，待编译与真实素材运行验收 |
| 严重程度 | Major |
| 建议优先级 | P1 |
| 主要模块 | `VideoFrameScheduler` |
| 关联模块 | `MultiViewRenderer`、运行指标展示链路 |

## 2. 问题摘要

应用选择“保持原始帧率”预览策略时，运行指标显示：

- 30 FPS 视频的调度丢帧率约为 20%。
- 120 FPS 视频的调度丢帧率约为 80%。

两个比例均指向实际预览提交速率收敛到约 24 FPS：

```text
(30 - 24) / 30 = 20%
(120 - 24) / 120 = 80%
```

该问题不是网络丢包、解码失败或 OpenGL 纹理重建造成的帧丢失，而是视频调度器落后于音频主时钟后主动丢帧追赶。120 FPS 场景还叠加了帧率边界判断错误。

## 3. 复现条件

已知现场条件：

- Windows 桌面环境。
- Qt 6.5.3 + MSVC Debug 构建。
- 视频使用硬件解码，解码输出经过硬件帧下载。
- 预览策略选择“保持原始帧率”。
- 播放速度为 1.0x。
- 测试素材分别为约 30 FPS 和 120 FPS。
- 现场日志中的输入帧需要执行 `NV12 -> YUV420P` 显示格式转换。

图像处理或视觉分析会进一步增加调度关键路径耗时，但不是本次现场现象成立的必要条件。

## 4. 复现步骤

1. 启动 TinyVideoProcessor。
2. 确认右侧“预览帧率策略”选择“保持原始帧率”。
3. 添加一段带音频的 30 FPS 视频并开始播放。
4. 等待运行指标完成至少两个采样周期。
5. 观察处理检查器中的“调度丢帧”与预览 FPS。
6. 停止或移除当前视频。
7. 添加一段带音频的 120 FPS 视频并开始播放。
8. 再次等待指标稳定并记录调度丢帧率。

建议复现时保持图像处理和视觉分析关闭，以隔离基础调度问题。

## 5. 实际结果与预期结果

### 5.1 实际结果

| 输入规格 | 实际预览表现 | 调度丢帧率 |
|---|---|---:|
| 30 FPS | 预览提交/绘制速率常落到约 24～29 FPS | 约 20% |
| 120 FPS | 未按约 8 ms 间隔调度，实际提交速率接近低帧率路径 | 约 80% |

调度器每次落后音频主时钟超过 40 ms 后，会连续弹出并释放过晚视频帧，直到重新进入同步窗口。

### 5.2 预期结果

- 30 FPS 普通视频在系统负载正常时，同步追帧丢帧应接近 0%，稳定采样窗口内建议不高于 2%。
- 120 FPS 输入必须识别为约 8 ms 帧间隔，不能回退到默认 33 ms。
- 如果产品选择受显示刷新率或性能策略限制高帧率预览，应将其统计为“预览降采样”，而不是“同步丢帧”。
- 视频处理耗时不应被额外叠加在完整帧间隔之后形成累计漂移。

## 6. 指标语义核对

界面中的“调度丢帧率”按相邻采样快照计算：

```text
droppedDelta / (submittedDelta + droppedDelta) * 100%
```

其中：

- `submittedDelta`：提交给预览输出链的帧数增量。
- `droppedDelta`：调度器主动丢弃的帧数增量。

当前 `schedulerDroppedFrames` 同时统计：

1. 音视频同步追帧丢弃。
2. 用户启用预览降帧后主动跳过的帧。

因此公式本身没有明显错误，但指标将两种不同语义合并，无法直接判断丢帧原因。本次在“保持原始帧率”条件下，主要来源为同步追帧。

## 7. 源码根因

### 7.1 根因一：120 FPS 被排除在帧间隔初始化范围外

`VideoFrameScheduler::Initialize()` 当前使用严格小于判断：

```cpp
if (frameRate > 0.0 && frameRate < 120.0) {
    frameIntervalMs_ = qRound(1000.0 / frameRate);
}
```

当输入恰好为 120 FPS 时条件不成立，`frameIntervalMs_` 保留默认值 33 ms，而不是正确的约 8 ms。

影响：

- 理论提交上限先被压到约 30 FPS。
- 再叠加格式转换、渲染入口和事件循环耗时后，实际速率可能接近 24 FPS。
- 音频时钟正常前进，视频帧持续被判断为过晚并主动丢弃。

### 7.2 根因二：每帧处理耗时叠加在完整固定间隔之后

当前成功提交一帧后的调度顺序为：

```text
弹出视频帧
  -> 显示格式转换
  -> 更新渲染状态
  -> 请求 OpenGL 重绘
  -> ScheduleNextFrame(scaledInterval)
```

也就是说，下一轮真实周期为：

```text
格式转换/提交耗时 + UI 事件循环耗时 + 完整帧间隔
```

对于 30 FPS，若同步处理约耗时 8 ms：

```text
33 ms + 8 ms ≈ 41 ms
1000 / 41 ≈ 24 FPS
```

该模型会持续累积相对音频主时钟的落后量，而不是只等待当前帧剩余的预算时间。

### 7.3 放大因素：显示格式转换位于同步调度关键路径

`MultiViewRenderer::PresentFrame()` 会同步调用 `VideoFrameConverter::ConvertToDisplayFrame()`。现场日志确认硬件解码输出为 NV12，并转换为 YUV420P 后进入渲染器。

该转换不是异常行为，但其耗时会被当前固定延时模型额外叠加，从而放大调度漂移。分辨率越高、并发流越多，影响越明显。

### 7.4 触发机制：超过同步阈值后主动追帧

音频同步模式下，调度器比较视频 PTS 与音频主时钟：

- 视频超前超过 40 ms：等待。
- 视频落后超过 40 ms：主动丢弃队首帧。
- 位于阈值内：提交显示。

因此高丢帧率是前述调度节奏错误的后果，丢帧分支本身是在执行既有的同步追赶职责。

## 9. 影响范围

### 9.1 用户影响

- 30 FPS 视频出现不必要的运动不连贯。
- 120 FPS 视频的大部分帧在调度阶段被丢弃，原始帧率预览语义不成立。
- UI 显示高丢帧率，但无法区分同步异常和主动预览降采样，容易误判为解码或网络问题。

### 9.2 功能影响

- 带音频文件源最容易稳定复现，因为音频主时钟持续推进。
- 无音频视频使用视频主时钟，表现可能不同，但仍受固定延时累计误差影响。
- 0.5x、1.5x、2.0x 播放速度可能进一步暴露等待时间未完全按媒体时间换算的问题。
- 多路播放共享 UI 事件循环，格式转换和多个调度定时器会互相增加延迟。
- 图像处理和视觉分析开启后会增加同步提交路径耗时，使丢帧进一步升高。

## 10. 临时规避方式

在正式修复前可以：

- 避免将 120 FPS 素材作为“原始帧率预览”验收依据。
- 对高帧率源主动选择“降低预览帧率”，并将结果理解为性能降级策略，而非原始帧率播放。
- 关闭图像处理和视觉分析，减少调度关键路径耗时。
- 减少同时播放的高分辨率、高帧率视频数量。

以上方式只能降低资源压力，不能修复固定延时累计漂移和 120 FPS 边界错误。

## 11. 推荐修复方案

### 11.1 第一阶段：修复调度正确性

建议仅修改 `VideoFrameScheduler`：

1. 对所有有限且大于 0 的合法帧率计算帧间隔，不再排除 120 FPS。
2. 音频同步模式改为由下一帧 PTS 与音频主时钟的差值决定剩余等待时间。
3. 等待时间按播放速度换算为墙钟时间。
4. 成功提交一帧后立即重新评估下一帧，不再无条件等待完整固定间隔。
5. 无音频视频使用相邻 PTS 与单调时钟计算绝对截止时间，避免处理耗时累计。
6. 在开始、暂停恢复、Seek、清空输出和速度切换时重置调度锚点。

不建议只把 `< 120.0` 改成 `<= 120.0` 后结束修复，因为这只能修复 120 FPS 的边界问题，无法消除 30 FPS 的累计漂移。

### 11.2 第二阶段：拆分运行指标

建议将 `schedulerDroppedFrames` 拆分为：

```text
lateDroppedFrames
previewRateLimitedFrames
```

UI 分别展示“同步追帧”和“预览降采样”，避免两种语义混合。

该阶段会涉及调度器、领域快照、应用层 DTO 和 UI 展示链路，应与调度正确性修复分开提交。

### 11.3 后续性能专题

调度正确性修复后，再基于新基线决定是否：

- 将 NV12/YUV420P 转换移出 UI 调度关键路径。
- 为高帧率源引入与显示刷新率关联的显式预览策略。
- 优化硬件帧下载、纹理上传或多路调度公平性。

上述内容不应混入本 Bug 的第一阶段修复。

## 13. 验收标准

### 13.1 正确性验收

- 30 FPS 带音频视频在 1.0x 下稳定播放，同步追帧丢帧率接近 0%，稳定窗口建议不高于 2%。
- 120 FPS 视频使用约 8 ms 源帧间隔，不再回退到 33 ms。
- 120 FPS 在显示器无法完整呈现时，渲染合并或主动降采样不得计入同步追帧。
- 0.5x、1.0x、1.5x、2.0x 均保持正确播放速度和音视频同步。
- 暂停恢复、Seek、停止重播后不出现持续突发丢帧。
- 无音频视频不出现过快播放、长时间等待或节奏漂移。
- 变帧率和无效 PTS 输入使用安全回退策略，不发生忙循环。

### 13.2 性能与稳定性验收

- UI 线程不存在持续 0 ms 忙循环。
- 多路调度不会因单路高帧率源长期饿死其他流。
- 帧队列容量保持有界，暂停、停止和关闭可正常退出。
- 纹理重建次数在稳定播放期间继续保持为 0。
- 修复前后记录相同素材、相同布局和相同开关条件下的预览 FPS、同步丢帧率、CPU、GPU 与内存数据。

## 15. 风险

- 修改调度时间模型会影响音视频同步、播放速度、暂停恢复和 Seek，不能只做静态验收。
- Qt 定时器在 Windows 上存在调度粒度和事件循环抖动，验收标准应允许少量短时波动。
- 120 FPS 是否全部提交给渲染器属于产品策略；若需要按显示刷新率降采样，必须显式定义并单独统计。
- 如果音频主时钟包含硬件缓冲提前量，现有 20 ms 补偿值需要在修复时保留或通过实测重新确认。
