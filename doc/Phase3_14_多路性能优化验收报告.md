# Phase 3.14 多路性能优化验收报告

## 验收结论

Phase 3.14 多路性能优化可以收口，允许进入 Phase 3.15 的 9/16 路真实播放扩容准入复核。

当前结论不是“性能已经足够支撑任意 9/16 路视频”，而是：

- 统一渲染路径已经具备可观测能力。
- `MultiViewRenderer` 的无效重绘和纹理重复重建已经得到控制。
- 用户可控预览降帧已经验证有效。
- 当前主要瓶颈已经从渲染后段逐步暴露到解码、硬件帧下载和格式转换前段。
- Phase 3.15 可以先推进 9 路真实播放扩容，16 路应作为实验支持或受限支持目标。

## 当前已完成优化

### 1. 性能指标定义

Phase 3.14.1 已明确多路播放时需要观察的指标：

- 渲染刷新频率。
- 纹理上传次数。
- 纹理重建次数。
- 可见流数量。
- 活跃帧流数量。
- 最大帧尺寸。
- CPU、GPU、内存人工观测数据。

这些指标为后续判断 9/16 路扩容是否可行提供了基础。

### 2. 轻量性能观测

`MultiViewRenderer` 已具备低频性能日志输出，能够观察类似信息：

```text
paintFps=11.8
visibleStreams=4
activeFrameStreams=4
attachedStreams=4
uploads=124
textureRebuilds=0
maxFrame=1920x1200
```

其中 `textureRebuilds=0` 是关键结果，说明纹理资源没有在播放过程中反复销毁重建。

### 3. 纹理资源复用

当前纹理只在尺寸或格式变化时重建。布局切换、active stream 切换、普通重绘不会导致全部纹理重建。

这说明渲染器资源管理已经从“可用”进入“可观察、可控”的状态。

### 4. 渲染刷新节流

`MultiViewRenderer` 已合并多路同时送帧造成的 UI update 请求。暂停状态下不会主动持续高频刷新。

这部分优化的意义是减少 UI 线程无效压力，而不是改变视频同步节奏。

### 5. 转换日志去重

`VideoFrameConverter` 的格式转换日志已经按签名去重，避免多路视频交替转换时刷屏。

日志现在用于确认转换类型，不再干扰性能观察。

### 6. 用户可控预览降帧

主窗口已增加：

- `原始帧率`
- `降帧预览`

默认保持原始帧率。用户启用降帧预览后，`VideoFrameScheduler` 会按 PTS 间隔跳过预览帧，减少后续格式转换、纹理上传和绘制压力。

人工观测结果：

```text
CPU 约降低 3%
GPU 约降低 5%
```

该结果说明策略有效，但收益有限。

## 性能基线记录

### 1 路普通视频

项目当前单路播放链路已经在 Phase 1、Phase 3.1 到 Phase 3.13 中持续验证。单路普通视频不是当前瓶颈。

当前结论：

- 单路普通视频可以稳定播放。
- 单路普通视频不构成进入 9 路扩容的主要风险。
- 后续如果需要简历级量化数据，可以补充单路 CPU/GPU/内存截图或日志，但不阻塞当前架构推进。

### 1 路 4K / MKV 视频

Phase 3.13 已完成非 `YUV420P` / 4K MKV 显示正确性方向的处理，当前渲染器统一接收可显示格式帧。

当前结论：

- 4K / MKV 的显示正确性已经从 Phase 3.14 的阻塞项移出。
- 4K 视频仍然可能带来较高格式转换和纹理上传压力。
- 多路 4K 不应作为 Phase 3.15 的默认验收规格。

### 4 路混合分辨率视频

用户人工观测场景包含多路混合源，其中有两路 `1920x1200@120fps` 高压力视频。

人工观测数据：

```text
GPU 60%+
CPU 15%+
内存 520MB+
```

开启降帧预览后：

```text
CPU 约降低 3%
GPU 约降低 5%
```

结论：

- 4 路混合播放已经具备基本可用性。
- 高帧率高分辨率源会明显拉高 GPU 压力。
- 仅在 `VideoFrameScheduler` 后段降帧，不能显著降低解码和硬件帧下载压力。

## 瓶颈判断

当前瓶颈不是单一模块造成的。

已经改善的部分：

- 重复纹理重建。
- 无效 UI 重绘。
- 多路日志刷屏。
- 渲染后段的部分无效预览帧处理。

仍然存在的主要压力：

- 高帧率源仍会持续进入解码链路。
- 硬解码后的硬件帧下载仍可能对 GPU/CPU 造成压力。
- 格式转换仍发生在真正进入渲染器之前。
- 多路高分辨率源会放大纹理上传成本。

因此，后续如果要继续显著降低 9/16 路资源占用，不能只继续改 `MultiViewRenderer`。更合理的后续专题是：

```text
解码输出 / 硬件帧转换前降载
```

该专题应单独设计，不应在当前 Phase 3.14 中临时塞入。

## 进入 Phase 3.15 的判断

### 9 路扩容

可以进入。

建议策略：

- 先以 3x3 的 9 路真实播放为目标。
- 验收视频优先使用普通分辨率视频，例如 720p / 1080p / 低帧率素材。
- 高帧率、高分辨率素材只作为压力测试，不作为基础通过标准。
- 默认允许用户开启降帧预览。

### 16 路扩容

不建议直接承诺完整正式支持。

建议策略：

- 作为实验支持或受限支持推进。
- 先验证 16 路创建、显示、停止、移除、关闭生命周期。
- 如果播放压力过高，应允许降级策略，例如限制高分辨率源数量、建议开启降帧预览，或只承诺低分辨率 16 路预览。

## 对简历项目的意义

Phase 3.14 的价值不在于把性能指标压到极限，而在于体现了完整的工程判断：

- 能建立指标。
- 能根据指标定位瓶颈。
- 能区分渲染后段优化和解码前段压力。
- 能把优化策略放在正确架构层级。
- 能明确扩容边界，不盲目承诺 16 路高规格播放。

这比单纯堆功能更适合简历项目表达。

## 残留风险

- 当前没有形成完整的 1 路普通视频、1 路 4K 视频精确量化表。
- 当前 4 路压力测试素材包含高帧率源，不能直接外推到所有 9/16 路场景。
- 16 路真实播放能力高度依赖机器性能、视频编码格式、分辨率、帧率和硬解能力。
- 后续 9/16 路扩容时可能暴露线程数量、队列容量、关闭耗时和资源释放方面的问题。

## 后续建议

下一步进入：

```text
Phase 3.15.1 9/16 路扩容准入复核
```

复核时应明确：

- 9 路的默认验收视频规格。
- 16 路是正式目标还是实验目标。
- 是否默认建议开启降帧预览。
- 是否把“解码输出 / 硬件帧转换前降载”登记为 Phase 3.15 之后的性能专题。
