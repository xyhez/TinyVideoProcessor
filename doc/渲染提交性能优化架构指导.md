# 渲染提交性能优化架构指导

## 1. 项目愿景

降低高帧率视频预览时 GUI 线程的重复格式转换开销，使 `MultiViewRenderer` 在一次 OpenGL 绘制前只处理每路最新待显示帧，并对常见 NV12 软件帧直接上传双平面纹理，避免不必要的 `NV12 -> YUV420P` CPU 转换。

本轮优化承接视频调度正确性修复，但不改变调度器、音频主时钟、解码线程和 UI 指标口径。

## 2. 设计原则

1. `PresentFrame()` 只完成所有权接管、最新帧替换和重绘请求，不执行像素格式转换。
2. 每路流最多保留一个待转换输入帧，后到帧直接替换尚未进入绘制的旧帧。
3. 格式转换推迟到 `paintGL()` 的实际绘制路径，每路每次绘制最多转换一帧。
4. 已成功显示的当前帧继续保留；新帧转换失败时不主动清空上一帧。
5. `ClearFrame()`、`DetachStream()` 和析构路径必须同时释放待转换帧与当前显示帧。
6. 保持 `IVideoFrameSink`、`SingleStreamFrameSinkAdapter` 和 `MultiViewRenderer::PresentFrame()` 公共接口不变。
7. 本轮不迁移 `VideoFrameScheduler` 线程，避免把图像处理、视觉分析配置和生命周期问题混入同一改动。
8. NV12 使用 Y 与 UV 双平面纹理直接绘制；其他格式继续通过现有 `VideoFrameConverter` 回退为 YUV420P。
9. NV12 Shader 根据帧的色彩范围和色彩空间选择转换参数，不能以性能优化为由牺牲基本色彩正确性。

## 3. 当前问题模型

当前流程先转换、后合并：

```text
VideoFrameScheduler
    -> MultiViewRenderer::PresentFrame
    -> ConvertToDisplayFrame
    -> 替换 currentFrame
    -> Qt 合并 update 请求
    -> paintGL 上传并绘制
```

120 FPS 输入而窗口实际约 60 次每秒绘制时，部分帧已经完成格式转换，却在 `paintGL()` 前被下一帧替换。转换成本已经发生，但结果没有上传或显示。

## 4. 目标状态模型

每路 `StreamRenderState` 分成两级帧状态：

- `pendingFrame`：最新待显示的输入帧，保持原始软件像素格式。
- `currentFrame`：可供纹理上传和重复绘制的 NV12 或 YUV420P 帧。

目标流程：

```text
PresentFrame
    -> 替换 pendingFrame
    -> 若已有 pendingFrame，记为一次渲染前合并
    -> RequestRenderUpdate

paintGL
    -> 取每路最新 pendingFrame
    -> NV12：保留原帧并直接上传 Y/UV 纹理
    -> 其他格式：ConvertToDisplayFrame 回退为 YUV420P
    -> 成功后替换 currentFrame
    -> 上传纹理并绘制
```

## 5. 生命周期

### 5.1 正常接收

- 新帧接管到 `pendingFrame`。
- `presentedFrames` 记录渲染器接收次数。
- 尚未绘制的旧 `pendingFrame` 被替换时增加 `coalescedFrames`。

### 5.2 绘制

- 只有存在 `pendingFrame` 时才准备新的显示帧。
- NV12 且直接渲染 Shader 可用时跳过转换器；其他格式才调用转换器。
- 准备成功后刷新当前显示帧元数据并标记纹理脏；实际发生格式转换时增加 `formatConvertedFrames`。
- 转换失败时保留上一张 `currentFrame`，避免画面无必要闪黑。

### 5.3 清理

- `ClearFrame()` 同时释放 `pendingFrame` 和 `currentFrame`，但保留纹理对象供后续复用。
- `DetachStream()` 和析构在释放两级帧后释放 OpenGL 纹理。

## 6. 功能 Phase

### Phase 0：文档与边界

- 创建本架构指导与独立 TODO。
- 验收：问题、状态模型、生命周期及不修改范围明确。

### Phase 1：转换前帧合并

- 为每路渲染状态增加待转换帧。
- 将格式转换从 `PresentFrame()` 移到实际绘制路径。
- 验收：一次绘制前多次提交只转换最新帧，接口及多路布局不变。

### Phase 2：诊断指标

- 增加接收、合并、转换和纹理上传计数。
- 验收：性能日志可以直接比较输入接收数与实际转换数。

### Phase 3：静态验收与运行回归

- 执行修改范围、空白、所有权和清理路径检查。
- 用户后续运行 120 FPS 素材，比较调度丢帧率和渲染日志。

### Phase 4：NV12 双平面直接渲染

- 为 NV12 构建 Y 单通道与 UV 双通道纹理上传描述。
- 增加 NV12 Shader，在 GPU 中完成色彩范围归一化和 YUV 到 RGB 转换。
- NV12 Shader 初始化失败或输入格式不支持时继续走 YUV420P 转换回退。
- 验收：NV12 日志中 `input=nv12`、`display=nv12`、`lastConverted=no`，且 `formatConverted` 不随正常 NV12 绘制增长。

## 7. 开发时间估算

| Phase | 预计耗时 | 不确定性 |
|---|---:|---|
| Phase 0～2：转换前合并与指标 | 2～3 小时 | Qt 绘制合并时机 |
| Phase 3：运行验收 | 1 小时 | 素材、Debug/Release 和机器负载 |
| Phase 4：NV12 直接渲染 | 2～4 小时 | OpenGL RG 纹理支持、Shader 色彩一致性 |

## 8. 最终呈现效果

- 高帧率输入不会对每个最终未显示的帧执行格式转换。
- OpenGL 仍只在 GUI 线程操作。
- 多路布局、点击聚焦、活动流选择和画面宽高比不变。
- 日志可观察 `received / coalesced / formatConverted / uploads` 的关系。
- NV12 输入不再执行 `sws_scale()`，只上传 Y/UV 两张纹理并由 GPU 完成颜色转换。

## 9. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| GUI 线程仍承担调度与 OpenGL 绘制 | 高负载下仍可能存在少量同步丢帧 | 本轮先消除确定的重复转换，运行数据不足时再独立设计线程迁移 |
| 转换失败 | 最新帧无法显示 | 保留上一张成功显示帧并沿用转换器日志 |
| 多路同时绘制 | 单次 paint 仍可能转换多帧 | 每路只转换最新一帧，后续可按可见性继续优化 |
| 指标计数语义变化 | 旧日志难直接横向比较 | 保留 `presentedFrames` 接收语义，新增独立合并与转换计数 |
| OpenGL 不支持 RG 双通道纹理或 NV12 Shader 链接失败 | 无法直接绘制 NV12 | 初始化时记录警告并自动回退到 YUV420P 转换路径 |
| 输入色彩元数据缺失 | 颜色可能偏差 | HD 默认采用 BT.709，SD 默认采用 BT.601；范围未指定时按有限范围处理 |

## 10. 不修改范围

- `MediaPipeline` 线程和生命周期。
- `VideoFrameScheduler` 同步、节奏和丢帧计数。
- `SyncManager` 与 `AudioPlayer`。
- 图像处理和视觉分析 sink。
- UI 运行指标 DTO 与展示文案。
- 解码器输出格式和硬件帧下载路径。

## 11. NV12 直接渲染数据流

```text
AV_PIX_FMT_NV12
    -> textureY：R8，尺寸 width x height
    -> textureUV：RG8，尺寸 ceil(width/2) x ceil(height/2)
    -> NV12 fragment shader
        -> 按 AVCOL_RANGE_* 归一化 Y/UV
        -> 按 AVCOL_SPC_* 选择 BT.601 / BT.709 / BT.2020 系数
        -> 输出 RGB
```

YUV420P 仍使用既有 Y、U、V 三个 R8 纹理和既有 Shader，确保非 NV12 输入兼容。
