# 单元测试学习指南（开发者够用版）

## 1. 先记住一句话

单元测试是用代码验证一小块代码在不同输入、状态和异常条件下是否符合预期。

它主要解决三个问题：

- 修改代码后，旧行为有没有被破坏。
- 边界和异常分支是否真的可用。
- 模块接口是否清晰、是否容易独立使用。

单元测试不负责证明整个软件完全正确，也不能替代真实视频、摄像头、网络和 UI 验收。

## 2. 测试层级

### 2.1 单元测试

测试一个函数、一个类或一个职责明确的小模块。

示例：

- `SyncQueue` 入队、出队、停止和唤醒。
- `PlaylistManager` 增删、去重和索引修正。
- `VisionConfigLoader` 处理合法与非法 JSON。

特点：运行快、结果稳定、失败位置明确。

### 2.2 集成测试

测试多个真实模块连接后的行为。

示例：

```text
MediaSource → Demuxer → Decoder → FrameQueue
```

它能发现接口、线程、资源和数据格式之间的问题，但运行成本高于单元测试。

### 2.3 系统测试

从用户视角测试完整程序。

示例：启动播放器，添加 9 路视频，执行暂停、移除和关闭。

当前项目的人工验收大多属于系统测试。

## 3. Qt Test、CTest、CI 的分工

```text
Qt Test：发现并执行一个测试程序内部的测试函数
CTest：启动多个测试程序并汇总退出码
CI：每次提交后自动完成配置、编译和 CTest
```

当前项目结构：

```text
CTest
  ├─ test_sync_queue.exe
  ├─ test_playlist_manager.exe
  ├─ test_vision_config_loader.exe
  └─ test_vision_pipeline_manager.exe
```

CTest 不理解 `QVERIFY`。它只判断测试程序最终返回 `0` 还是非 `0`。

## 4. 一个 Qt Test 是怎样运行的

最小结构：

```cpp
#include <QtTest>

class CalculatorTest : public QObject {
    Q_OBJECT

private slots:
    void additionReturnsSum();
};

void CalculatorTest::additionReturnsSum()
{
    const int result = 2 + 3;
    QCOMPARE(result, 5);
}

QTEST_APPLESS_MAIN(CalculatorTest)

#include "calculator_test.moc"
```

执行流程：

```text
QTEST_APPLESS_MAIN 生成 main()
  → main() 创建 CalculatorTest
  → QTest::qExec() 读取元对象信息
  → moc 提供 private slots 列表
  → qExec() 调用 additionReturnsSum()
  → QCOMPARE 记录成功或失败
  → qExec() 返回最终退出码
```

注意：

- `QTEST_APPLESS_MAIN` 是宏，不是普通函数。
- 它生成 `main()`，但不负责逐个硬编码调用测试函数。
- moc 为 `Q_OBJECT` 类生成元对象信息。
- qExec 只执行符合 Qt Test 规则的测试槽，不执行所有成员函数。

## 5. 测试函数的基本结构：AAA

推荐把测试分成三段：Arrange、Act、Assert。

```cpp
void PlaylistManagerTest::moveNextSelectsSecondItem()
{
    // Arrange：准备对象和输入
    PlaylistManager manager;
    manager.AddFiles({"a.mp4", "b.mp4"});

    // Act：执行一个需要验证的行为
    const bool moved = manager.MoveNext();

    // Assert：检查结果
    QVERIFY(moved);
    QCOMPARE(manager.CurrentIndex(), 1);
}
```

一个测试尽量只描述一个行为。失败时应能从测试名看出哪里不符合预期。

## 6. 应该测试哪些情况

对一个公开接口，至少考虑下面五类。

### 6.1 正常路径

```text
输入正常时，能否得到正确结果？
```

例如队列按照先进先出返回元素。

### 6.2 边界条件

```text
空、一个、最大值、最小值、最后一项时会怎样？
```

例如：

- 空播放列表调用 `MoveNext()`。
- 队列容量为 1 时连续入队。
- 删除播放列表最后一项。

### 6.3 非法输入

```text
错误参数会被拒绝、修正还是回退？
```

例如：

- 非法 JSON 回退默认视觉配置。
- 重复 pipeline ID 被跳过。
- 播放列表忽略空路径。

### 6.4 状态转换

```text
对象从一个状态切到另一个状态时，旧状态是否正确清理？
```

例如：

```text
未激活 → 激活 OpenCV → 切换 YOLO → 关闭视觉分析
```

需要检查 Startup、Shutdown、当前 ID 和失败后的状态。

### 6.5 生命周期与并发

```text
停止、销毁、超时、等待和唤醒是否安全？
```

例如：消费者阻塞在空队列时，`InterruptWait()` 是否能让它退出。

## 7. 常用断言

### 7.1 QVERIFY

检查布尔表达式：

```cpp
QVERIFY(manager.MoveNext());
QVERIFY(!manager.CurrentItem().has_value());
```

### 7.2 QCOMPARE

比较实际值和期望值：

```cpp
QCOMPARE(manager.CurrentIndex(), 1);
QCOMPARE(result.pipelines.size(), 2);
```

失败时会显示实际值和期望值，通常优先于：

```cpp
QVERIFY(manager.CurrentIndex() == 1);
```

### 7.3 QVERIFY2

为失败补充信息：

```cpp
QVERIFY2(file.open(QIODevice::ReadOnly), "测试配置文件打开失败");
```

### 7.4 QSignalSpy

观察 Qt 信号：

```cpp
QSignalSpy spy(&manager, &PlaylistManager::PlaylistChanged);

manager.AddFile("a.mp4");

QCOMPARE(spy.count(), 1);
```

它适合验证信号次数和参数，但不能替代对象最终状态检查。

## 8. 初始化与清理

Qt Test 支持以下特殊槽函数：

```cpp
private slots:
    void initTestCase();
    void cleanupTestCase();
    void init();
    void cleanup();
```

执行顺序：

```text
initTestCase()             整个测试类开始前一次

init()
testA()
cleanup()

init()
testB()
cleanup()

cleanupTestCase()          整个测试类结束后一次
```

使用原则：

- 测试之间不要共享会被修改的状态。
- 每个测试都应能单独运行。
- 公共对象可以在 `init()` 中重新创建。
- 临时文件、线程和资源必须在测试结束时释放。

## 9. 数据驱动测试

同一种行为需要验证多组输入时，不必重复写多个测试函数。

```cpp
private slots:
    void clampThreshold_data();
    void clampThreshold();
```

准备数据：

```cpp
void ProcessorTest::clampThreshold_data()
{
    QTest::addColumn<int>("input");
    QTest::addColumn<int>("expected");

    QTest::newRow("小于下限") << -1 << 0;
    QTest::newRow("正常值") << 128 << 128;
    QTest::newRow("超过上限") << 300 << 255;
}
```

执行测试：

```cpp
void ProcessorTest::clampThreshold()
{
    QFETCH(int, input);
    QFETCH(int, expected);

    QCOMPARE(ClampThreshold(input), expected);
}
```

数据驱动测试适合输入输出表，不适合行为差异很大的场景。

## 10. Fake、Stub 和 Mock

测试经常不能直接连接真实依赖。

### 10.1 Stub

只返回预设结果。

```text
调用 LoadModel() 永远返回 true。
```

### 10.2 Fake

提供简化但可工作的实现。

当前 `test_vision_pipeline_manager.cpp` 中的 `FakePipeline` 会记录 Startup、Shutdown 和 started 状态，属于 Fake。

### 10.3 Mock

除了返回结果，还验证调用行为。

```text
Startup 必须调用一次；Shutdown 不能调用两次。
```

对普通开发者，优先手写小型 Fake。只有调用关系复杂时再考虑 GoogleMock 等 Mock 框架。

## 11. 并发测试怎么写

并发测试最容易出现“偶尔失败”。重点不是让测试等待足够久，而是建立明确同步条件。

当前队列测试使用：

- `std::promise` 表示工作线程已经开始。
- `std::future::wait_for` 设置等待上限。
- CTest 为整个测试程序设置 15 秒超时。
- `--repeat until-fail:10` 重复运行，检查偶发问题。

不推荐：

```cpp
QThread::sleep(3);
QVERIFY(threadProbablyFinished);
```

推荐：

```cpp
QVERIFY(future.wait_for(1s) == std::future_status::ready);
```

并发测试必须保证失败路径也能唤醒并回收线程，否则测试本身可能卡死。

## 12. 什么不适合单元测试

下面这些场景通常需要集成测试或人工验收：

- 真实摄像头能否打开。
- 某个 RTSP 地址是否稳定。
- FFmpeg 对特定视频的完整解码效果。
- OpenGL 最终画面是否正确。
- YOLO 模型真实精度和推理性能。
- 9/16 路播放的 CPU、GPU 和内存占用。

可以把其中的纯逻辑拆出来单测，例如：

- RTSP 重连状态机。
- StreamId 与 slot 的映射。
- YOLO 输出张量解析。
- 坐标映射和 NMS。

硬件和外部环境留给更高层测试。

## 13. 好测试的特征

### 快

单元测试通常应在毫秒级完成，整套测试应方便频繁运行。

### 稳定

同一份代码重复运行，结果应一致。避免依赖网络、系统时间、随机数和本机固定路径。

### 独立

测试顺序改变后仍能通过，单独运行某个测试也能通过。

### 可读

测试名直接描述行为：

```cpp
void missingFileFallsBackToDefaults();
```

比下面的名称更有信息：

```cpp
void testConfig1();
```

### 只检查公开行为

不要为了测试直接访问大量私有成员。测试过度依赖实现细节后，正常重构也会造成大量测试失败。

## 14. 常见错误

### 一个测试验证太多内容

失败后不知道是哪条行为有问题。应按行为拆分。

### 只测试正常路径

真实 bug 常出现在空值、边界、失败和状态切换。

### 只检查函数返回值

必要时还要检查对象状态、信号、资源和调用次数。

### 使用真实外部依赖

网络或摄像头失败不代表业务逻辑错误，会让测试不稳定。

### 用长时间 sleep 解决并发问题

机器快慢会改变结果。应使用条件、future、信号或事件同步。

### 为了通过测试修改正确需求

先判断测试预期是否正确，再判断生产代码是否有 bug。

### 追求覆盖率数字

覆盖率只能说明代码被执行过，不能说明断言有效。优先覆盖高风险行为，而不是追求 100%。

## 15. 当前项目的最低测试策略

本项目不需要一开始测试所有模块。推荐优先级：

### 必须单测

- 纯算法和转换函数。
- 状态机。
- 配置解析与默认值。
- 队列和并发控制。
- 列表、映射和索引逻辑。
- 失败后容易造成资源或状态错误的 manager。

### 适合后续集成测试

- Demuxer + Decoder。
- Seek 和 Flush。
- 无音频视频。
- 网络中断和关闭。
- 帧格式转换。

### 保留人工验收

- UI 操作体验。
- 画面质量。
- 摄像头兼容性。
- 多路性能。
- YOLO 实际效果。

## 16. 日常开发流程

修复 bug：

```text
先写一个能复现 bug 的失败测试
  → 修复生产代码
  → 测试通过
  → 运行完整测试集确认没有回归
```

开发新功能：

```text
明确公开行为和边界
  → 完成最小实现
  → 补正常、边界、失败测试
  → 运行完整测试集
```

小型 UI 调整不必强行写单元测试。优先把测试时间投入状态、算法、并发和资源生命周期。

## 17. 当前项目测试命令

启用测试：

```powershell
cmake -S . -B build/unit-tests `
  -DCMAKE_PREFIX_PATH=<Qt安装目录> `
  -DTINY_VIDEO_BUILD_TESTS=ON
```

构建：

```powershell
cmake --build build/unit-tests --target `
  test_sync_queue `
  test_playlist_manager `
  test_vision_config_loader `
  test_vision_pipeline_manager
```

运行全部测试：

```powershell
ctest --test-dir build/unit-tests --output-on-failure
```

重复运行：

```powershell
ctest --test-dir build/unit-tests --repeat until-fail:10 --output-on-failure
```

只运行名称包含 `queue` 的测试：

```powershell
ctest --test-dir build/unit-tests -R queue --output-on-failure
```

## 18. 写完测试后的检查表

- 测试名是否说明了输入条件和预期行为？
- 是否区分了准备、执行和断言？
- 是否覆盖正常、边界和失败路径？
- 是否只依赖可控制的输入？
- 是否检查了最终状态，而不只是返回值？
- 测试能否单独运行？
- 重复运行结果是否稳定？
- 失败时是否能快速判断原因？
- 是否清理了线程、文件和临时资源？
- 这个场景真的适合单元测试吗？

## 19. 建议练习顺序

1. 阅读 `test_playlist_manager.cpp`，理解正常、边界、状态和信号测试。
2. 阅读 `test_vision_config_loader.cpp`，理解临时文件和错误输入测试。
3. 阅读 `test_vision_pipeline_manager.cpp`，理解 Fake 和生命周期测试。
4. 最后阅读 `test_sync_queue.cpp`，理解 future、阻塞和超时。
5. 自己为 `PlaylistManager::SetCurrentIndex()` 补充非法索引测试。
6. 尝试把阈值边界改写成数据驱动测试。

对当前项目而言，掌握到这里已经足以支撑日常开发和秋招面试，不需要先学习复杂测试平台或追求完整测试体系。
