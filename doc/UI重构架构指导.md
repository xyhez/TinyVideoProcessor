## 1. 文档信息

- 功能名称：Fincept 风格专业视频分析工作台 UI 重构
- 开发分支：`dev_ui_refactor`
- 文档状态：方案已确认，Phase 0～Phase 4 已完成静态验收，下一阶段为 Phase 5 真实运行指标
- 适用范围：主窗口、UI 主题、视频源列表、属性面板、播放控制区及其直接展示状态

## 2. 项目愿景

TinyVideoProcessor 已具备本地文件、摄像头、RTSP、多路播放、统一 OpenGL 多视口渲染、图像处理和视觉分析能力，但当前主界面仍以功能验证型布局为主：播放控制、多路流管理、图像处理和视觉识别控件处于同一视觉层级，难以体现“专业多路视频处理平台”的产品定位。

本次重构希望将主界面升级为一个适合长时间使用和项目展示的专业视频分析工作台：

- 视频画面始终是界面主体。
- 用户可以快速添加、选择、启动和移除媒体源。
- 当前活动视频、活动音频、播放状态和异常状态清晰可见。
- 图像处理与视觉分析参数集中在当前视频属性面板中。
- 播放控制保持高频、稳定、易发现。
- 主题、间距、控件状态和颜色语义形成可复用的 UI 体系。

最终目标不是复刻金融终端，而是形成具有 TinyVideoProcessor 自身语义的“深色专业视频终端”。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 学习 C++、Qt、FFmpeg、OpenGL 和 OpenCV 的开发者。
- 需要同时预览文件、摄像头和网络流的使用者。
- 需要在活动视频上切换图像处理或视觉识别任务的使用者。
- 面试、作品集或技术演示场景中的项目评审者。

### 3.2 核心使用场景

1. 添加一个或多个文件、摄像头或 RTSP 视频源。
2. 在 `Single`、`2x2`、`3x3`、`4x4` 布局间切换。
3. 点击画面或视频源条目切换活动视频。
4. 为活动视频选择活动音频、图像处理模式和视觉分析管线。
5. 对文件源执行播放、暂停、停止、Seek、速度和音量控制。
6. 识别实时流、离线流、活动视频和活动音频的状态。
7. 双击画面进入单路聚焦，再恢复多画面布局。
8. 进入全屏观看，并保持播放与处理状态不丢失。

## 4. 当前 UI 基线与主要问题

### 4.1 当前能力

当前 `MainWindow` 已经具备：

- 文件播放列表与上一项、下一项、播放模式。
- 多路视频源列表。
- 添加文件、摄像头和 RTSP 视频源。
- 移除视频源、设置活动视频和活动音频。
- 全部启动、暂停和停止。
- 播放、暂停、Seek、音量、静音和播放速度。
- `Single`、`2x2`、`3x3`、`4x4` 布局。
- 原始帧率与降帧预览切换。
- 图像处理开关、模式和阈值设置。
- 视觉分析管线与识别结果叠加开关。
- 全屏、鼠标自动隐藏和双击单路聚焦。

### 4.2 当前问题

- 左侧同时堆叠播放列表、多路流列表和大量操作按钮，信息边界不清晰。
- 底部一行同时承载播放、音量、速度、布局、预览帧率、图像处理、视觉分析和全屏，窗口缩小时容易拥挤。
- 中英文文案混用，产品名称仍显示为 `modernFFplay-V2.0`。
- 菜单栏和状态栏存在但没有形成有效信息层级。
- 视频源状态主要依赖文本，不易快速识别活动视频、活动音频、实时流和异常流。
- 图像处理和视觉分析参数与播放控制混排，不符合使用频率层级。
- 缺少统一的颜色、字体、间距、边框和控件状态规范。
- `MainWindow` 已经较大，不能继续将所有视觉构建和状态格式化逻辑堆入同一文件。

## 5. 功能边界

### 5.1 本次重构范围

- 建立原创的深色终端 UI 主题。
- 将产品标题统一为 `TinyVideoProcessor`。
- 重构主窗口为顶部状态区、命令区、左侧视频源区、中央视频区、右侧属性区、底部播放区和底部状态区。
- 将现有控件迁移到符合使用频率和功能语义的位置。
- 统一中文文案、状态颜色、控件间距和交互反馈。
- 增强视频源列表的活动视频、活动音频、播放和错误状态表达。
- 将现有图像处理与视觉分析控件迁入右侧属性面板。
- 调整多视口活动边框颜色，使其与新主题一致。
- 在数据链路明确后，增加视频画面浮层和真实运行指标。
- 保持现有播放、多路管理、图像处理和视觉分析行为不退化。

### 5.2 第一里程碑范围

第一里程碑只包含：

- 主题基础。
- 主窗口布局骨架。
- 现有控件迁移。
- 现有状态的重新展示。
- 静态检查和人工测试说明。

第一里程碑不增加跨层运行指标，不在 UI 中写死 FPS、分辨率、编码格式或丢包率。

### 5.3 暂不包含

- 解码、同步、队列、音频、图像处理或视觉推理算法重构。
- 新增 RTMP、HTTP-FLV、自动重连等媒体能力。
- 新增 OCR、分割、报警、存储或历史查询。
- 用 QML、Electron 或 Web 技术重写 UI。
- 复制 Fincept Terminal 的源码、资源或商标。
- 为了 UI 重构修改公共媒体接口或数据格式。
- 未经确认直接引入第三方 UI 框架或图标库。

## 6. 设计原则

### 6.1 视频优先

中央多视口区域应占据窗口最大面积。侧栏、属性面板和工具栏不得无必要地压缩视频画面。

### 6.2 高频操作优先

添加视频源、布局切换、播放控制和全屏属于高频操作，应始终可见；阈值、识别模型等高级参数应进入右侧属性面板。

### 6.3 状态必须真实

UI 只能展示来自现有状态或正式新增接口的数据。未提供的数据使用 `--` 或不展示，不允许用常量伪造真实运行指标。

### 6.4 保持架构边界

`MainWindow` 只负责控件初始化、状态展示、事件转发和页面级布局；播放控制继续通过 `MediaPlayController`，播放列表规则继续由 `PlaylistManager` 提供，UI 不直接访问解码器、同步器、音频输出或线程队列。

### 6.5 渐进式迁移

优先保留现有控件对象名和信号连接。先完成视觉结构，再逐步提取可复用组件和新增状态接口，每个 Phase 都应具备独立验收条件。

### 6.6 不影响播放性能

QSS、列表绘制、状态刷新和画面浮层不得引入高频对象创建或阻塞渲染线程。运行指标应采用低频采样或已有统计结果，不在每帧触发复杂 UI 更新。

### 6.7 原创与许可安全

可以借鉴深色终端、细边框、紧凑工具栏和状态色编码等通用设计规律，但必须使用 TinyVideoProcessor 自己的布局、文案、图标和代码实现。

### 6.8 中文可读性

普通标签、菜单和按钮使用适合中文的无衬线字体；时间、FPS、分辨率、编码格式等技术数据可使用等宽字体。不得为了模仿终端风格而让全部中文使用不合适的等宽字体。

## 7. 目标界面结构

```text
┌ TinyVideoProcessor │ ● LIVE │ 4 / 9 路 │ 58 FPS │ 当前时间 ┐
├ 添加文件 │ 添加摄像头 │ 添加 RTSP │ 全部启动/暂停 │ 布局 ┤
├────────────┬──────────────────────────┬──────────────┤
│ 视频源      │                          │ 当前视频      │
│            │                          │              │
│ 文件/实时流 │       多路视频预览         │ 基本信息      │
│ 活动/音频   │                          │ 图像处理      │
│ 播放/异常   │                          │ 视觉分析      │
├────────────┴──────────────────────────┴──────────────┤
│ 上一项 │ 播放/暂停/停止 │ 进度 │ 时间 │ 速度 │ 音量 │ 全屏 │
├ READY │ Active: 当前视频 │ Audio: 当前音频 │ Vision: 当前管线 ┤
└──────────────────────────────────────────────────────┘
```

### 7.1 顶部产品状态区

- 左侧显示 `TinyVideoProcessor`。
- 中部显示全局运行状态、已用流数量、可用容量和后续真实渲染 FPS。
- 右侧预留全屏、设置或窗口级操作。
- 第一里程碑只展示已有真实数据；不存在的数据不显示或显示 `--`。

### 7.2 顶部命令区

- 添加文件、添加摄像头、添加 RTSP。
- 全部启动、全部暂停、全部停止。
- 多视口布局选择。
- 采用文本加简洁图标，保留工具提示和禁用状态。

### 7.3 左侧视频源区

- 第一阶段复用现有 `QListWidget`，统一条目文本和选中态。
- Phase 3 使用 `QStyledItemDelegate` 与 `QListWidgetItem` 自定义数据角色绘制名称、来源类型和状态标识，不为每一路创建独立 QWidget。
- 列表按 `StreamId` 原位更新条目，保留选择和双击命中，避免 16 路刷新时反复销毁展示控件。
- 活动视频与活动音频必须使用不同的可识别标志，不能只依赖颜色。
- 文件播放列表与多路视频源语义应明确；可通过分页、分组或统一媒体源模型逐步收口，但第一阶段不得改变 `PlaylistManager` 行为。
- 当前 Controller 没有逐流播放状态查询或状态变化信号；Phase 3 不从按钮命令推断第二套播放状态，非活动流只表达“已加载”，逐流播放状态推迟到只读状态边界完成后实现。
- `StreamErrorOccurred` 没有恢复或清错信号，因此条目只能表达“最近错误”，不能宣称错误仍在持续；元数据随流移除同步清理。

### 7.4 中央多视频区

- 继续由 `MultiViewRenderer` 负责视频帧、布局、点击命中、双击聚焦和活动边框。
- UI 布局不得创建额外的渲染副本。
- 第一阶段只调整外围容器和活动边框主题。
- 后续浮层显示视频名称、状态、分辨率和 FPS 时，应与 OpenGL 渲染生命周期兼容。

### 7.5 右侧当前视频属性区

- 只展示和编辑当前活动视频的属性。
- 第一阶段包含：预览帧率、图像处理开关、处理模式、阈值、视觉管线和识别叠加。
- 采用“基本信息 / 图像处理 / 视觉分析”的分页或分组结构。
- 没有活动视频时整体禁用，并显示明确空状态。
- 右侧面板应可折叠，避免小窗口下过度压缩视频区域。

### 7.6 底部播放控制区

- 只保留上一项、播放、暂停、下一项、进度、时间、速度、音量、静音和全屏。
- 当前项目不存在单路停止按钮；`pushButton_stopAll` 继续位于顶部命令区并仅表示“全部停止”，不得为了对齐设计稿改变其语义。
- 实时流不支持 Seek 时，进度条禁用并显示 `LIVE`。
- 高级图像处理和视觉分析控件不得再次混入该区域。

### 7.7 底部状态区

- 展示全局就绪、加载、播放或错误状态。
- 展示当前活动视频、活动音频和视觉管线。
- 状态栏只承载摘要，不重复右侧属性面板的详细参数。

## 8. 视觉系统

### 8.1 颜色令牌

建议先建立以下语义令牌，具体色值可在实现和视觉验收时微调：

| 令牌 | 建议色值 | 用途 |
|---|---:|---|
| `BackgroundBase` | `#070A0D` | 窗口和视频外围背景 |
| `BackgroundSurface` | `#0D1217` | 侧栏、属性面板、工具栏 |
| `BackgroundRaised` | `#131A21` | 输入框、按钮、选中行 |
| `BorderDim` | `#202A33` | 普通分隔线 |
| `BorderBright` | `#34424F` | 聚焦和悬停边框 |
| `TextPrimary` | `#E6EDF3` | 主文字 |
| `TextSecondary` | `#98A6B3` | 次要说明 |
| `TextMuted` | `#64727F` | 禁用和弱提示 |
| `Accent` | `#F59E0B` | 活动视频、选中项、主要操作 |
| `Technical` | `#22D3EE` | 分辨率、FPS、编码等技术信息 |
| `Positive` | `#22C55E` | LIVE、播放正常、就绪 |
| `Warning` | `#FBBF24` | 重连、实验容量、性能警告 |
| `Negative` | `#EF4444` | 离线、断流、错误和危险操作 |

颜色只表达语义，不作为唯一信息载体。重要状态应同时具备文字或图标。

### 8.2 字体

- 中文 UI：优先使用系统可用的中文无衬线字体。
- 技术数据：优先使用系统等宽字体。
- 产品标题、区块标题和普通标签建立明确字号层级。
- 最小正文应保证常见桌面缩放比例下可读。

### 8.3 间距与边框

- 采用紧凑但可点击的桌面端密度。
- 主要区块使用 1 像素分隔线，不依赖大阴影。
- 圆角保持克制，避免大面积卡片化。
- 工具栏、列表条目和表单控件应使用统一高度。

### 8.4 图标

- 第一阶段优先使用 Qt 标准图标或项目自有的简单线性图标。
- 引入第三方图标库前必须确认许可证和新增依赖影响。
- 禁止复制参考项目的图标资源。

### 8.5 控件状态

所有按钮、输入框、下拉框、列表条目和标签至少考虑：

- 默认。
- 悬停。
- 按下。
- 选中或激活。
- 禁用。
- 聚焦。
- 警告或错误。

## 9. 整体架构

### 9.1 分层边界

```text
Presentation Layer
  MainWindow
    ├─ 页面布局与控件状态
    ├─ UI 主题应用
    ├─ 视频源展示模型/委托
    ├─ 当前视频属性面板
    └─ 播放与全局命令转发
              │
              ▼
Application Layer
  MediaPlayController
    ├─ 播放命令
    ├─ 多路流命令
    ├─ active stream / active audio stream
    ├─ 图像处理设置
    └─ 视觉分析设置
              │
              ▼
Domain / Infrastructure
  MultiStreamManager / MediaPipeline / Renderer / Vision Pipeline
```

### 9.2 UI 主题模块

不允许继续在 `MainWindow` 中散落大段 `setStyleSheet()` 字符串。推荐建立独立主题模块：

```text
src/ui/theme/
  UiTheme.h
  UiTheme.cpp
```

职责：

- 集中维护颜色、字体和控件样式。
- 对外提供应用级样式表或主题应用入口。
- 不保存播放状态，不依赖 Controller 或基础设施层。
- 后续可以扩展亮色主题，但本次只实现深色主题。

若开发时确认 Qt 资源系统更符合现有构建方式，可以改为 `QSS + qrc`；变更前应先更新本文档和 TODO，不在实现中临时混用两种方案。

### 9.3 MainWindow 职责

允许：

- 组装页面级布局。
- 将 UI 事件转发给 `MediaPlayController` 或 `PlaylistManager`。
- 订阅状态信号并更新控件。
- 维护窗口级展示状态，例如面板折叠、全屏和鼠标隐藏。
- 将现有流状态转换为展示文本和 UI 角色。

不允许：

- 直接控制 Demuxer、Decoder、AudioPlayer 或视频调度线程。
- 在 UI 中计算解码 FPS、丢包率或推理结果。
- 创建第二套播放、活动流或视觉管线状态。
- 为了展示方便绕过 Controller 修改领域对象。

### 9.4 视频源展示

第一阶段继续由 `MainWindow::RefreshStreamView()` 使用现有数据刷新列表，避免同时进行 UI 重构和数据模型重构。

当条目需要展示更多状态时，推荐引入仅属于 Presentation Layer 的展示结构：

```cpp
struct StreamPresentationState {
    StreamId id;
    QString displayName;
    QString sourceType;
    QString statusText;
    bool active;
    bool activeAudio;
    bool realtime;
    bool error;
};
```

该结构只负责展示，不拥有播放对象，也不替代领域状态。若所需状态当前无法从 Controller 获得，应暂停并先设计应用层只读接口。

### 9.5 当前视频属性面板

属性面板继续调用已有 Controller 接口：

- 预览降帧设置。
- 图像处理启用状态。
- 图像处理模式与阈值。
- 当前视觉管线。
- 识别结果叠加状态。

面板自身不保存独立参数副本；所有可变状态以 Controller 信号或查询结果为准。

### 9.6 多视口渲染器

`MultiViewRenderer` 继续拥有：

- 多视口布局计算。
- 视频帧绘制。
- 活动视频边框。
- 点击和双击命中。

Phase 4.1 只修改活动边框、普通边框和槽位底色等直接视觉常量，不调整 framebuffer 坐标、边框宽度、帧上传、shader、宽高比和点击命中。

Phase 4.2 已完成三种浮层方案预研：

| 方案 | 优点 | 主要风险 | 结论 |
| --- | --- | --- | --- |
| `QPainter + 原生 OpenGL` 混合绘制 | Qt 官方支持，直接复用 `Viewport::qtRect`，无需额外控件 | 每帧发生 Painter/OpenGL 状态切换；必须严格维护 `beginNativePainting()`/`endNativePainting()` 边界；渲染器需接收 UI 文案 | 可行，但不作为首版 |
| `StreamViewportOverlay` 透明子控件 | OpenGL 帧路径不变；展示状态留在 UI 层；后续真实指标可低频独立刷新 | 需维护尺寸、层级、透明鼠标穿透，并运行验证不同平台的合成效果 | Phase 4 首选 |
| OpenGL 字体或文字纹理 | 可完全留在 GPU 绘制链 | 中文字形、缓存、DPI、混合、上下文丢失和 Qt 版本兼容复杂 | 不采用 |

Phase 4.3 新增 UI 层只读覆盖层，作为 `MultiViewRenderer` 子控件存在：

- 覆盖层通过 `MultiViewRenderer::Viewports()` 读取逻辑坐标，不读取 framebuffer 坐标，也不参与视频帧绘制。
- 覆盖层设置鼠标穿透、无焦点和透明背景；点击与双击继续由渲染器处理。
- 覆盖层监听渲染器尺寸和显示事件，并在整表刷新时主动置顶；覆盖区域始终使用渲染器逻辑尺寸，生命周期由父子对象关系管理。
- `MainWindow` 在现有 `RefreshStreamView() -> RefreshMultiViewRenderer()` 链路中整表同步只读展示快照，不新增第二套状态信号链。
- 首版只显示真实名称、来源、实时源属性、活动视频、活动音频和“最近错误”；缺失项不展示。
- `LIVE` 只表示实时源类型，“最近错误”只表示历史错误记录；不推断逐流播放状态，不展示伪造 FPS、分辨率、编码或在线状态。
- 覆盖层不持有媒体对象，不访问 Controller；`MultiViewRenderer` 不依赖 `StreamPresentationState` 或其他 UI 类型。

### 9.7 状态数据流

```text
用户操作
  -> MainWindow
    -> MediaPlayController / PlaylistManager
      -> MultiStreamManager / MediaPipeline

播放与配置状态
  -> Controller signal
    -> MainWindow 展示转换
      -> 工具栏 / 视频源列表 / 属性面板 / 状态栏

视频帧
  -> VideoFrameScheduler
    -> FrameSink
      -> MultiViewRenderer

未来运行指标
  -> 基础设施层低频统计
    -> 应用层只读快照或信号
      -> UI 低频刷新
```

## 14. 风险与依赖

| 风险 | 影响 | 应对策略 |

| `MainWindow` 继续膨胀 | 可维护性下降 | 主题、列表展示和格式化职责按收益逐步提取 |

| 图标依赖 | 引入额外许可和构建负担 | 第一阶段使用 Qt 标准图标或项目自有资源 |

## 16. 当前决策记录

1. 采用 Fincept Terminal 风格所代表的深色、紧凑、状态驱动视觉语言，但不复刻其产品页面。
2. 使用 Qt Widgets 继续实现，不切换到 QML 或 Web 技术。
3. 第一里程碑先完成主题、布局和现有功能迁移。
4. 保留 `MultiViewRenderer` 作为唯一常规视频显示区域。
5. 第一里程碑不伪造 FPS、分辨率、编码格式和丢包率。
6. 真实运行指标必须通过应用层只读边界进入 UI。
7. 默认使用中文操作文案，协议名、编码名、模型名等技术术语保留英文。
8. 默认不引入第三方 UI 框架和图标库。
9. 默认仅做静态检查，编译、运行和测试需用户明确要求。
10. 本次 UI 重构使用独立分支 `dev_ui_refactor` 开发。
11. Phase 2 使用 `splitter_workspace` 组织左、中、右工作区，子项顺序固定为 `widget_sourcePanel`、`widget_centerPanel`、`widget_inspectorPanel`，中央区域索引保持为 1。
12. Phase 2 的全屏行为继续沿用整个 `MainWindow` 全屏，不在布局重构阶段引入仅视频区可见的影院模式。
13. Phase 2 只展示静态工作区标识和现有真实状态；FPS、分辨率、编码、容量等指标继续推迟到 Phase 5 的真实数据接口完成后展示。
14. Phase 3 使用单个 `QStyledItemDelegate` 绘制紧凑视频源条目，以自定义数据角色传递纯展示状态；Delegate 不访问 Controller，不使用 `setItemWidget()`。
15. Phase 3 在 UI 层只记录来源类型、是否实时、显示名称和最近错误，不持有媒体源或管线对象；活动视频、活动音频和有无音频每次刷新时从 Controller 读取。
16. 当前没有可靠逐流播放状态，Phase 3 禁止将 Controller 全局 `PlaybackState` 展示为每一路的播放状态。
17. 用户已确认进入 Phase 4；多视口边框可修改渲染器直接视觉常量，但保持 2/4 framebuffer 物理像素边框宽度和现有绘制顺序不变。
18. Phase 4 浮层采用 UI 层透明 `StreamViewportOverlay`，不在 `paintGL()` 中混合文字绘制，也不向基础设施层传递 UI 展示类型。
19. Phase 4 浮层首版只复用 Phase 3 的可靠展示状态；逐流播放状态、FPS、分辨率和编码继续等待 Phase 5 的只读数据边界。
20. Phase 4 透明子控件保留 QWidget 默认父内容传播，不使用 `WA_NoSystemBackground` 或 `CompositionMode_Source` 清空整块区域，降低覆盖 QOpenGLWidget 合成内容的风险。
21. Phase 4 小视口降级顺序为“视频名称优先、来源徽章其次、状态徽章按可用宽高展示”，系统字体增大时不得强行绘制越界内容。
