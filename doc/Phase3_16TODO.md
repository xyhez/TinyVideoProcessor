# TODO: Phase 3.16 多路真实场景量化验收

## 当前定位

- 当前状态：暂缓执行。
- 创建目的：作为项目完结时的统一量化验收参考。
- 当前不做：不运行程序、不采集数据、不新增代码、不调整性能策略。
- 前置结论：
  - Phase 3.15 已完成 9/16 路真实播放扩容验收。
  - 9 路作为正式支持能力。
  - 16 路作为实验支持能力。
  - 高负载下程序不崩溃，但不承诺所有机器、所有视频规格都满帧稳定。

## 阶段目标

在项目接近完结时，对多路文件源、摄像头源、后续网络流或图像处理场景进行统一量化验收，形成可用于 README、项目报告和简历描述的数据支撑。

本阶段重点不是继续扩大功能，而是回答以下问题：

- 当前项目在常见机器上能稳定承载多少路。
- 不同路数下 CPU、GPU、内存占用如何。
- 降帧预览、视频规格、硬解能力对性能有什么影响。
- 哪些能力可以正式承诺，哪些只能作为压力测试或实验能力。

## 架构边界

- 不改变 `MainWindow` 的 slot 分配职责。
- 不改变 `MediaPlayController` 的应用层控制职责。
- 不改变 `MultiStreamManager` 的多路生命周期职责。
- 不改变 `MediaPipeline` 的单路播放管线职责。
- 不让 `MultiViewRenderer` 管理播放管线生命周期。
- 不为了量化验收临时加入补丁式性能逻辑。
- 如果量化数据暴露架构问题，先新增独立优化 TODO，再进入代码修改。

## 暂缓原因

- 当前 9/16 路扩容主线已经完成，不需要立刻用量化验收阻塞后续功能推进。
- 量化验收更适合在摄像头、网络流或图像处理能力基本稳定后统一执行。
- 如果现在过早采集数据，后续功能加入后仍需要重新测一遍。

## 风险与沟通点

- 最终性能数据会强依赖测试机器，不应直接泛化为所有环境。
- 16 路应持续保持实验支持表述，除非后续有充分量化数据证明可正式承诺。
- 如果量化数据显示瓶颈集中在解码或硬件帧下载，不应只在 `MultiViewRenderer` 内做补丁式优化。
- README 和简历中的性能指标必须和本 TODO 后续采集的数据一致。
