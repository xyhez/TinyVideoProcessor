## 1. 项目一句话说清（三个版本）

### 1.1 30 秒极简版（简历自述用）

> TinyVideoProcessor 是一个基于 Qt6 + FFmpeg + OpenCV 的多路视频处理框架，从单路播放器渐进演进到支持文件、摄像头、RTSP 网络流的多源多路平台，具备统一 OpenGL 多画面渲染、图像处理链和 YOLO/OpenCV 视觉分析能力，目前正式支持 9 路真实播放，实验支持 16 路。

### 1.2 2 分钟版（面试常规介绍用）

> 这是我个人独立设计和实现的一个视频处理框架，从 2026 年 5 月启动，做了大约 2 个月。项目一开始是一个基础的 FFmpeg 播放器，我按照渐进式演进的思路把它重构成分层架构，然后逐 Phase 扩展：
>
> - **Phase 0-1**：架构重构 + 播放器基础功能（Seek、播放列表、播放速度、音量、全屏）。
> - **Phase 2**：接入 USB 摄像头，做设备枚举和参数选择，把 `IMediaSource` 抽象验证起来。
> - **Phase 3**：这是最重的一块，做了单路 `MediaPipeline` 抽取、`MultiStreamManager` 多路管理、`VideoFrameScheduler` 抽取、统一 `MultiViewRenderer` OpenGL 多画面渲染、多路布局与聚焦、格式适配、性能优化，最后完成 9/16 路扩容。
> - **Phase 4**：接入 RTSP 网络流，把异常关闭、断流移除、重连的生命周期串起来。
> - **Phase 5-8**：图像处理基础链、多视觉处理器架构（`IVisionPipeline`）、OpenCV 轮廓 + YOLO ONNX 检测、以及 JSON 配置化。
>
> 整个项目最大的特点是**架构演进有清晰的边界**：每个 Phase 都是可运行、可验收的完整版本，不是功能堆砌。

### 1.3 5 分钟版（技术面深度介绍用）

在 2 分钟版基础上，重点展开：

1. **架构分层**：四层——UI（MainWindow）、应用层（MediaPlayController）、领域层（IMediaSource / MediaPipeline / MultiStreamManager）、基础设施层（Demuxer / Decoder / VideoFrameScheduler / MultiViewRenderer / Vision）。每层职责单一，通过接口而非具体类交互。
2. **核心设计模式落地**：策略（IMediaSource）、管道（MediaPipeline）、装饰器（ImageProcessingFrameSink）、管理器（MultiStreamManager）、适配器（SingleStreamFrameSinkAdapter）、工厂（VisionProcessorFactory）、观察者（Qt 信号槽）。
3. **两条关键数据流**：控制流从 MainWindow 逐层下沉；帧流从 IMediaSource 经解复用、解码、调度、图像处理、视觉分析、显示 sink 最后汇入 MultiViewRenderer 统一渲染。
4. **工程实践**：`AVPacket` / `AVFrame` 队列做了 RAII 重构，用 `unique_ptr + 自定义 deleter` 管理生命周期；视觉任务用 JSON 配置化，缺失或非法时回退默认管线。

## 2. 完整自述稿（可背可默）

> 我做的这个项目叫 TinyVideoProcessor，核心目标是探索**一个视频处理框架从基础播放器到多路视频分析平台的渐进演进过程**。技术栈是 C++20、Qt6、FFmpeg、OpenCV、OpenGL 和 ONNX。
>
> **为什么做这个项目**：⬇️ 补充（例如：想系统性练一次 C++ 多媒体项目的架构演进；想把 FFmpeg / OpenCV / OpenGL 一次性串起来；想做一个能进简历、能持续演进的作品）。
>
> **做的最有价值的三件事**：
>
> 1. **架构分层与演进**。从最初 MainWindow 直接持有 demuxer、decoder、renderer 的紧耦合状态，重构为四层分层。领域层引入 `IMediaSource` 抽象后，文件、摄像头、RTSP 三种源可以复用同一套播放管线。这种抽象让我从单路走到多路时，成本非常低——`MultiStreamManager` 只是管理若干个 `MediaPipeline` 实例，`MediaPipeline` 本身不感知 `StreamId`。
> 2. **统一 OpenGL 多画面渲染**。传统做法是每路一个 QOpenGLWidget，但那样纹理不能复用，多路切换、聚焦、格式适配都很难做。我选了单 OpenGL 上下文 + 多纹理的方案，抽取 `MultiViewRenderer`，通过 `StreamId → slot → viewport` 映射统一绘制。这让 Single、2x2、3x3、4x4 布局共用一套代码，双击聚焦也只是切换布局，不动 stream 生命周期。
> 3. **调度与显示解耦**。原本 `VideoRender` 内部同时做同步判断、丢帧、绘制。我把调度层拆到独立的 `VideoFrameScheduler`，负责取帧、AUDIO/VIDEO sync 时钟比对、丢帧追赶和下一轮 `QTimer::singleShot()`；`VideoRender` 收敛为默认单路显示 sink；`MultiViewRenderer` 只做绘制。这一层解耦让图像处理和视觉分析可以以「装饰器」形式插在调度器和显示 sink 之间，不改动同步逻辑。
>
> **难点在哪**：
>
> - **音视频同步**：AUDIO sync 下按音频主时钟判帧早晚，帧过早等待、过晚丢帧，同时按播放速度修正帧间隔。
> - **多路资源开销**：从 4 路推到 9/16 路的过程中，纹理频繁重建、UI update 抖动、硬件帧下载都成了瓶颈，做了纹理复用、刷新节流、预览降帧等一系列优化。
> - **异常与生命周期**：RTSP 打开失败、断流移除、关闭时中断都需要正确回收；摄像头释放链路也做了单独审查。
> - **视觉推理不阻塞播放**：目前是同步推理，YOLO 复杂模型会拖累播放流畅度，Phase 9 会做异步推理和降帧分析。
>
> **收获**：⬇️ 补充（例如：第一次把架构层次落到实处；第一次系统性做性能定位；对 FFmpeg 帧生命周期有了工程级理解等）。

## 3. 架构讲述稿（图 + 一段话）

面试官经常让你「上白板画一下架构」，或者「讲讲你的架构分层」。请准备**一张能徒手画出来的分层图**和**一段能顺下来的解释**。

### 3.1 徒手可画的四层图

```text
┌────────────────────────────────────────────┐
│ UI 层        MainWindow / Dialogs          │
├────────────────────────────────────────────┤
│ 应用层       MediaPlayController           │
├────────────────────────────────────────────┤
│ 领域层       IMediaSource（策略）           │
│              MediaPipeline（管道）          │
│              MultiStreamManager（管理）     │
├────────────────────────────────────────────┤
│ 基础设施层   Demuxer / Decoder             │
│              VideoFrameScheduler           │
│              AudioPlayer / SyncManager     │
│              ImageProcessingFrameSink      │
│              VisionProcessingFrameSink     │
│              MultiViewRenderer (OpenGL)    │
└────────────────────────────────────────────┘
```

### 3.2 一段话讲清楚

> UI 只负责交互和信号转发，不直接持有底层组件。应用层 `MediaPlayController` 对 UI 屏蔽单路和多路细节。领域层是核心——`IMediaSource` 抽象让文件、摄像头、RTSP 复用同一套后端；`MediaPipeline` 是单路播放管线，不感知 `StreamId`；`MultiStreamManager` 负责 `StreamId` 分配、active stream 和 active audio stream 策略。基础设施层是可插拔的能力实现，帧从解复用、解码、调度、图像处理、视觉分析一路走到 `MultiViewRenderer` 统一渲染。

### 3.3 关键设计模式对应

| 模式 | 落地位置 | 解决的问题 |
| :--- | :--- | :--- |
| 策略 | `IMediaSource` + 三种实现 | 媒体源可扩展，播放管线不用改 |
| 管道 | `MediaPipeline` 组合各基础设施组件 | 单路播放链路职责单一 |
| 装饰器 | `ImageProcessingFrameSink` / `VisionProcessingFrameSink` | 默认透传，启用后叠加处理，不改主链 |
| 管理器 | `MultiStreamManager` | 多路生命周期、active stream 语义 |
| 适配器 | `SingleStreamFrameSinkAdapter` | 单路 sink 语义适配到多路渲染 |
| 工厂 | `VisionProcessorFactory` + `VisionConfigLoader` | JSON 驱动，视觉管线可配置化实例化 |
| 观察者 | Qt 信号槽 | 位置、时长、错误、聚焦等事件解耦 |

## 4. 核心亮点 STAR 案例（重点练熟）

> STAR = Situation（背景）/ Task（目标）/ Action（做法）/ Result（结果）
> 建议：**先挑 3 个熟到能答任意追问的**，别贪多。下面的案例是根据项目内容预填的骨架，具体数字和细节按你的实际情况调整。

### 4.1 亮点一：从单路到多路的架构演进

**S**：项目最初只支持单路文件播放，`MainWindow` 直接持有 Demuxer、Decoder、AudioPlayer、VideoRender，紧耦合。要扩展多路时，如果沿用这个结构会导致 `MainWindow` 承担大量重复逻辑。

**T**：在不破坏单路播放能力的前提下，抽出一条可复用的单路播放管线，并在其之上组合多路管理，同时把音频从多路场景中降级为单路输出。

**A**：
- 引入领域层 `MediaPipeline`，把 Demuxer、Decoder、AudioPlayer、SyncManager 组合进去，对上只暴露 `Start / Pause / Stop / Seek` 等接口，**不持有 StreamId**。
- 引入 `MultiStreamManager`，负责 `StreamId` 分配、若干 `MediaPipeline` 生命周期、active stream 和 active audio stream 策略——即同一时刻最多一路输出音频。
- 应用层 `MediaPlayController` 对 UI 屏蔽单路 / 多路差异，UI 只调用统一入口。

**R**：从单路到多路的扩展没有污染原有代码，`MediaPipeline` 复用度极高。摄像头源和 RTSP 源接入时，只是新增 `IMediaSource` 实现，多路管线自动可用。

**面试官会追问**：
- 为什么 `MediaPipeline` 不感知 StreamId？→ 因为 StreamId 是多路管理的概念，让单路管线感知它就等于把多路耦合下沉。
- active audio stream 切换的时候，其他 stream 的音频怎么办？→ ⬇️ 补充实际做法（例如 mute / 静默解码 / 暂不解码音频等）。
- 多路时如何避免 UI 卡死？→ 各 `MediaPipeline` 有自己的解码线程；UI 只处理位置、状态信号。

---

### 4.2 亮点二：MultiViewRenderer 统一 OpenGL 多画面渲染

**S**：多路播放最直接的实现是每路一个 `QOpenGLWidget`，但这样每路都需要独立的 OpenGL 上下文和纹理，切换布局、双击聚焦、切换 active stream 都会破坏纹理状态，性能和实现复杂度都不理想。

**T**：用单个 OpenGL 上下文承载所有画面，支持 Single、2x2、3x3、4x4 布局，支持双击聚焦并恢复，不同源、不同分辨率、不同帧格式的帧都能进入统一渲染管线。

**A**：
- 抽取 `MultiViewRenderer`（QOpenGLWidget 子类），维护 `StreamId → slot → viewport` 映射；每个 slot 一个 GL 纹理，只在尺寸或格式变化时重建。
- 引入 `SingleStreamFrameSinkAdapter`，把不感知 StreamId 的单路 sink 语义适配为「投递到指定 stream 的 slot」。
- 抽取 `VideoFrameConverter`，把非 `YUV420P` 软件帧（如 `NV12`、`P010`、4K MKV 常见格式）统一转成渲染器可接受的显示格式。
- 布局切换只调整 slot 分配和 viewport，不销毁 stream；双击聚焦切到 `Single` 布局也保留其他 stream 生命周期。

**R**：一套 `MultiViewRenderer` 统一承载 Single / 2x2 / 3x3 / 4x4 布局。9 路真实播放作为正式能力通过验收，16 路作为实验能力通过验收。纹理重建次数在正常操作下稳定为 0。

**面试官会追问**：
- 为什么不用每路一个 widget？→ 上下文和纹理无法复用；切换和聚焦要销毁重建，抖动明显。
- 你们的纹理格式是什么？→ ⬇️ 补充（例如 `YUV420P` 三平面纹理 + Fragment Shader 做色彩空间转换）。
- 16 路的瓶颈在哪？→ 瓶颈从渲染后段转移到解码前段（硬件帧下载、格式转换），Phase 3.14 已经把 `textureRebuilds=0` 达成。

---

### 4.3 亮点三：VideoFrameScheduler 抽取与音视频同步

**S**：原本 `VideoRender` 同时做同步判断、丢帧、绘制，职责混杂。要接入图像处理和视觉分析，必须把「什么时候取帧」和「怎么显示这帧」分开。

**T**：抽出独立的调度层，负责取帧、同步判断、丢帧和自调度；显示 sink 只负责「接收可显示帧」这个纯粹语义。

**A**：
- 新建 `VideoFrameScheduler`，输入包括 `VFrame_` 队列、`SyncManager`、帧率、视频 time base、播放速度；输出是 `IVideoFrameSink::PresentFrame(frame)`。
- 逻辑：查看队首帧但不提前弹出；AUDIO sync 下按音频主时钟判早晚，过早等待、过晚丢帧、可显示则弹出并转交 sink；VIDEO sync 下刷新视频主时钟；按播放速度修正帧间隔；`QTimer::singleShot()` 自调度。
- `MediaPipeline` 显式组合 scheduler 和 sink，把 sink 注入到 scheduler。

**R**：`VideoRender` 收敛为默认单路显示 sink；`MultiViewRenderer` 只做绘制；`ImageProcessingFrameSink` 和 `VisionProcessingFrameSink` 可以以装饰器形式插在 scheduler 和 sink 之间，完全不改同步逻辑。

**面试官会追问**：
- 音视频同步的三种策略？→ AUDIO / VIDEO / EXTERNAL；本项目主要用 AUDIO sync，无音频流场景退化为 VIDEO sync。
- 播放速度是怎么实现的？→ ⬇️ 补充（例如：视频侧调整帧间隔，音频侧 sonic / 变速不变调；或音频调采样率、视频跟随音频钟）。
- 无音频视频怎么办？→ Phase 3.0 明确了无音频流支持，退化为按视频钟自驱。

---

### 4.4 亮点四：RTSP 网络流生命周期与异常处理

**S**：网络流和本地文件的区别在于「随时可能异常」——地址错误、连接超时、中途断流、服务恢复、关闭中断都需要正确应对。

**T**：让 RTSP 源复用同一套 `MediaPipeline` 和 `MultiViewRenderer`，同时把异常场景全部走完。

**A**：
- 新增 `NetworkMediaSource : public IMediaSource`，通过 `AVDictionary` 设置 `rtsp_transport=tcp`、`max_delay`、`buffer_size` 等参数。
- Phase 4.5 专门做了「网络异常与关闭链路审查」，覆盖打开失败提示、断流后自动移除该 stream、服务恢复后可重新加入、播放中关闭窗口正常回收。
- 保持 active stream / active audio stream 策略与文件源、摄像头源一致。

**R**：RTSP 与文件源、摄像头源在多路场景下混播不冲突；异常场景不会导致主程序崩溃或资源泄漏。

**面试官会追问**：
- `rtsp_transport=tcp` 为什么？→ UDP 丢包会导致画面撕裂；TCP 更稳，代价是延迟略高。
- 断流是怎么检测到的？→ ⬇️ 补充（例如 `av_read_frame` 长时间超时、`avformat` 返回 EOF / 错误码）。
- RTMP / HTTP-FLV 什么时候做？→ Phase 4 已经完成评估报告，属于后续扩展。
- 自动重连怎么设计？→ ⬇️ 补充（可讲：退避策略、上限重试、恢复后重新加入 slot）。

### 4.5 亮点五：视觉分析管线 + 配置化（OpenCV + YOLO）

**S**：图像处理和视觉分析是两回事——处理是「改图」，分析是「输出结构化结果」。前者可以在原帧上叠加，后者需要独立管线管理不同算法、不同参数、不同后端。

**T**：设计一套多视觉处理器架构，支持 OpenCV 传统检测和 YOLO ONNX 推理，能通过 JSON 配置切换参数，缺失或非法时回退默认。

**A**：
- 定义 `IVisionPipeline` 接口，实现 `OpenCvContourVisionPipeline` 和 `YoloVisionPipeline`。
- `VisionPipelineManager` 负责注册、单激活切换、懒加载和运行入口，同一时刻只运行一条 pipeline，且只处理 active stream。
- `VisionProcessingFrameSink` 插在图像处理 sink 之后，`RunActive()` 后再调 `VisionOverlayRenderer` 叠加检测结果。
- 配置层：`config/vision_pipelines.json` + `VisionConfigLoader` + `VisionProcessorFactory`。JSON 支持 `opencv-contour` 的 threshold/maxValue，以及 `yolo-onnx` 的 modelPath / labelsPath / inputWidth / inputHeight / confidenceThreshold / nmsThreshold。
- YOLO 用 OpenCV DNN 加载 ONNX，模型文件不进 git，默认路径 `models/yolo.onnx`。

**R**：一条 JSON 即可切换视觉任务和参数，无需重新编译。第一版覆盖了传统视觉和深度学习两个方向。

**面试官会追问**：
- 为什么用 OpenCV DNN 而不是 ONNX Runtime？→ OpenCV DNN 依赖少、和已有 OpenCV 链复用；性能不是极致但足够第一版。后续可切 ORT / TensorRT。
- YOLO 推理阻塞主流程怎么办？→ 当前是同步的，简单模型 OK，复杂模型会影响帧率；Phase 9 会做异步推理、降帧分析和结果缓存。
- 单激活模式为什么？→ 第一版避免多管线争抢和 overlay 冲突，聚焦「能跑起来 + 能配置」。
- NMS 是什么？→ Non-Maximum Suppression，抑制重叠框，保留置信度最高的检测结果。

### 4.6 备选亮点：队列 RAII 重构

**S**：早期 `SyncQueue` 通过 `std::function<void(T)> deleter_` 保存释放函数，`AVPacket` / `AVFrame` 的释放依赖调用方约定，容易泄漏或 double free。

**T**：把 FFmpeg 资源的释放责任交给 RAII 所有权类型，队列只做搬运。

**A**：
- `src/core/ffmpeg_raii.h` 定义 `AVPacketDeleter` / `AVFrameDeleter`，配 `AVPacketPtr = unique_ptr<AVPacket, AVPacketDeleter>` 和对应的 `AVFramePtr`。
- `SyncQueue<T>` 收敛职责，去掉 deleter，只做 move 入队、move 出队和线程同步。清队列直接 `raw_queue_.clear()`，容器元素析构自动释放。
- Packet / Frame 队列全部迁移到 `SyncQueue<AVPacketPtr>` / `SyncQueue<AVFramePtr>`。

**R**：释放 API `av_packet_free()` / `av_frame_free()` 集中在 deleter；调用方不再关心释放；泄漏和 double free 风险消除。

**面试官会追问**：
- 为什么不用 `shared_ptr`？→ 队列是所有权转移语义，`unique_ptr + move` 更贴合；`shared_ptr` 会引入不必要的引用计数开销。
- move-only 类型进队列有什么坑？→ 需要 `emplace` / `push(std::move(...))`；容器和接口签名都要相应调整。

## 5. 面试常见问题池

> 建议每题都写下自己的答案，能背最好。空的部分是给你回忆用的。

### 5.1 架构与设计

1. **为什么要做分层架构？直接一个 MainWindow 打天下不行吗？**
   > 参考答案：MainWindow 打天下意味着 UI、播放控制、资源管理全部耦合；每次加功能都要动 MainWindow；测试也没法做。分层的价值是**变化被约束在每一层内**——加媒体源只动领域层，加渲染方式只动基础设施层。

2. **`IMediaSource` 抽象了什么？为什么这么设计？**
   > 参考答案：抽象了「一个 FFmpeg 可打开的输入」，只暴露 `Open / Close / GetFormatContext / GetSourceInfo / GetType`。播放管线依赖这个接口就够了，不关心是文件、摄像头还是网络流。

3. **说说你项目里的设计模式落地**
   > 见第 3.3 节。

4. **`MediaPipeline` 为什么不感知 `StreamId`？**
   > 参考答案：`StreamId` 是多路管理的概念，属于 `MultiStreamManager` 的领域。让 pipeline 感知它就等于把多路耦合下沉到单路层，未来单独嵌入单路场景就不干净。

### 5.2 多媒体基础

5. **FFmpeg 的 Demuxer / Decoder 分别做什么？**
   > 参考答案：Demuxer 把封装格式（mp4/mkv/flv/rtsp）拆成 `AVPacket`（压缩数据 + 时间戳）；Decoder 把 packet 解成 `AVFrame`（原始像素 / PCM 采样）。

6. **音视频同步的三种策略？你用的哪种？**
   > 参考答案：AUDIO / VIDEO / EXTERNAL。本项目默认 AUDIO sync——音频驱动主时钟，视频按主时钟判断早晚。无音频流退化为 VIDEO sync。

7. **Seek 是怎么实现的？**
   > 参考答案：`av_seek_frame()` 定位到关键帧 → 清空 packet / frame 队列 → 让 decoder flush → 重新解码。要注意 seek 精度依赖 GOP 大小。⬇️ 补充实际实现细节。

8. **播放速度是怎么实现的？**
   > ⬇️ 补充。可参考 `Phase1_1_任务9_播放速度控制实现报告.md`。

9. **无音频视频怎么处理？**
   > 参考答案：Phase 3.0 明确了退化路径——AUDIO sync 不可用时用 VIDEO sync；`AudioPlayer` 不启动；`SyncManager` 用视频主时钟。

10. **硬件解码怎么开的？**
    > ⬇️ 补充。可能涉及 DXVA2 / D3D11 / NVDEC 等，注意讲清楚硬件帧下载的开销。

### 5.3 性能与优化

11. **9/16 路扩容遇到的瓶颈？**
    > 参考答案：瓶颈从渲染后段转移到解码前段。渲染侧通过纹理复用、update 节流、`textureRebuilds=0` 已经比较健康；前段硬件帧下载和格式转换是主要 CPU 占用点。

12. **纹理为什么不能频繁重建？**
    > 参考答案：GL 纹理创建 / 销毁是重操作，涉及显存分配和上下文同步；频繁重建会导致渲染抖动。只在尺寸或格式变化时重建是必要的约束。

13. **多路刷新如何避免 UI 抖动？**
    > 参考答案：合并同一帧内的多个 update 请求；暂停状态下不高频刷新；预览降帧作为用户可控开关。

14. **CPU 占用如何优化？**
    > ⬇️ 补充实际数据。可讲的方向：硬解、软解降分辨率、预览降帧、异步推理。

### 5.4 视觉与算法

15. **`opencv-contour` 管线做了什么？**
    > 参考答案：灰度 → 阈值二值化 → 轮廓检测 → 绘制。适合光照稳定、背景简单的规则检测场景。参数 threshold / maxValue 通过 JSON 配置。

16. **YOLO ONNX 推理流程？**
    > 参考答案：读模型 → 预处理（resize / normalize / blob）→ `net.forward()` → 后处理（confidence 过滤 + NMS）→ 输出 boxes。`inputWidth`/`inputHeight` / 阈值都在 JSON 里。

17. **YOLO 推理阻塞播放怎么办？**
    > 参考答案：当前是同步推理，简单模型 OK，复杂模型会影响帧率。Phase 9 计划做异步推理（帧到达后放推理队列）+ 降帧分析（不是每帧都推理）+ 结果缓存（下一帧沿用上帧的检测结果 overlay）。

18. **为什么 OpenCV DNN 而不是 ONNX Runtime？**
    > 参考答案：依赖少、和已有 OpenCV 复用、跨平台。性能不是极致但足够第一版；未来可以切 ORT 或 TensorRT。

19. **NMS 是什么？为什么需要？**
    > 参考答案：Non-Maximum Suppression。同一目标可能被多个候选框覆盖，NMS 保留置信度最高的、抑制与其重叠度高的其他框。

### 5.5 工程与实践

20. **队列 RAII 重构为什么要做？**
    > 参考答案：见 4.6 节。核心是把释放责任从「调用方约定」转移到「所有权类型」，消除泄漏和 double free。

21. **智能指针在你项目里怎么用？**
    > 参考答案：`unique_ptr` 表达单一所有权（`AVPacketPtr` / `AVFramePtr` / 各 pipeline 组件）；`shared_ptr` 用于 `IMediaSource` 被多方持有的场景。

22. **多线程怎么设计的？**
    > ⬇️ 补充。至少讲清楚：Demuxer 线程、Decoder 线程（音 / 视各一个）、AudioPlayer 线程、UI 线程；队列作为线程间边界。

23. **配置化为什么用 JSON 而不是 XML / INI？**
    > 参考答案：JSON 结构化好、层次清晰、Qt / std 都有成熟解析；参数嵌套自然（如 params 对象）。缺失或非法时回退默认是产品化的最小闭环。

24. **项目里最难 debug 的一个 bug？**
    > ⬇️ 补充（例如：某个 seek 后帧对不齐、某个 4K MKV 显示花屏、RTSP 断流没走到清理、YOLO 输入形状不对等）。

25. **如果重做一遍，你会怎么做？**
    > ⬇️ 补充。第 7 节有一些方向可以参考。

## 7. 反思与不足（面试官爱问「你觉得哪里还不好」）

**当前限制**：

- **16 路播放性能依赖机器**：不承诺所有分辨率、编码格式都满帧稳定，属于实验能力。
- **YOLO 推理是同步的**：复杂模型会影响播放帧率，Phase 9 需要异步 + 降帧 + 缓存。
- **RTMP / HTTP-FLV / 自动重连尚未实现**：Phase 4 只做到 RTSP。
- **配置持久化未做**：音量、播放速度、布局、active stream 等偏好未落盘。
- **无自动化测试**：目前靠人工验收，测试覆盖是短板。
- **无 SQLite / 报表**：视觉分析结果无持久化，无历史查询。

**如果重做会怎么做**：

- 更早引入 `VideoFrameScheduler` 抽象（现在是 Phase 3.10 才做，前期同步逻辑散在 `VideoRender` 里）。
- 视觉分析一开始就设计异步管线，不要走同步路径再返工。
- 早期就做多路准入压测，而不是等到 Phase 3.15 才把 16 路真实跑起来发现瓶颈。
- 配置化更早引入，避免硬编码参数分散在各个 processor。

**面试官若追问「你从这个项目学到了什么」**：

- ⬇️ 补充。参考方向：架构演进的边界感（每层只解决自己的问题）、性能优化的定位方法（先测量、再优化）、抽象的时机（不要过早、也不能太晚）。
