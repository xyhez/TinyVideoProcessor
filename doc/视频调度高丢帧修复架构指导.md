# 视频调度高丢帧修复架构指导

## 1. 项目愿景

修复原始帧率预览时30 FPS视频约20%、120 FPS视频约80%的异常调度丢帧，使视频调度节奏能够补偿同步处理耗时，并正确支持120 FPS输入，同时保持既有音视频同步、播放速度、Seek、暂停恢复和多路渲染边界。

本轮目标是恢复调度正确性，不借机重构解码、音频、渲染、图像处理或视觉分析链路。

## 2. 设计原则

1. 音频主时钟仍是带音频视频的同步依据，不改变 `SyncManager` 和 `AudioPlayer` 的时钟语义。
2. 保留现有40 ms同步追帧阈值与20 ms音频时钟补偿，避免在同一修复中同时改变多个时序参数。
3. 源帧率只负责提供无音频或同步窗口内的基础节奏，不再从“当前处理完成时刻”重新等待完整间隔。
4. 使用单调时钟和绝对截止时间消除格式转换、渲染入口及事件循环耗时造成的累计漂移。
5. 120 FPS是合法输入边界，不得回退到默认33 ms间隔。
6. 调度器仍只负责取帧、同步判断、主动丢帧和节奏安排，不承担像素转换或OpenGL绘制。
7. 本轮不拆分运行指标；同步追帧和预览降采样指标拆分作为后续独立改动。

## 3. 当前问题模型

当前成功提交一帧后的周期为：

```text
处理耗时 + 完整帧间隔
```

30 FPS场景中，33 ms帧间隔叠加约8 ms转换和调度耗时后，会退化到约24 FPS。音频主时钟持续推进，视频落后超过40 ms后触发主动丢帧。

120 FPS还存在独立边界问题：初始化只接受小于120的帧率，恰好120 FPS时继续使用默认33 ms间隔。

## 4. 整体架构

修复后的调度仍保持原有数据流：

```text
VideoFrameScheduler::Tick
    -> 查看队首PTS
    -> 与SyncManager主时钟比较
        -> 超前：等待现有同步差值
        -> 过晚：丢帧追赶
        -> 可显示：弹出并提交
    -> 使用单调时钟计算下一绝对截止时间
    -> 只等待截止时间剩余预算
```

### 4.1 双层调度职责

第一层是同步决策：

- AUDIO sync继续使用视频PTS与音频主时钟比较。
- VIDEO sync继续在提交或预览降采样时刷新视频主时钟。
- 超前等待、过晚丢弃和可显示三种决策保持现有语义。

第二层是基础节奏：

- `frameIntervalMs_`由所有有限且大于0的源帧率计算。
- 调度器启动时开启单调时钟并清空截止时间状态。
- 第一次提交后，下一截止时间锚定为“本轮开始时间 + 帧间隔”。
- 后续截止时间在上一次绝对截止时间上累加，不从处理完成时刻重新计算。
- 下一次定时只等待“截止时间 - 当前时间”的剩余部分。
- 若已明显落后，立即调度下一轮，并在超过一个间隔时重锚，避免无界追赶和长期0 ms忙循环。

### 4.2 状态重置边界

以下操作必须重置基础节奏锚点：

- `Start()`。
- `Stop()` / `Pause()`。
- `SetSpeed()`成功切换速度。
- `ClearOutputFrame()`，覆盖Seek和输出清理链路。

预览降采样的PTS基线继续按现有规则单独重置，不与基础节奏状态混用。

### 4.3 不修改的边界

本轮不修改：

- `MediaPipeline`的线程和生命周期编排。
- `SyncManager`主时钟实现。
- `AudioPlayer`硬件延迟与时钟刷新逻辑。
- `Decoder`硬件帧下载。
- `MultiViewRenderer`格式转换、纹理上传和绘制。
- 图像处理与视觉分析sink。
- UI指标DTO和展示文案。

## 5. 关键算法

### 5.1 帧间隔初始化

```text
有限且frameRate > 0
    -> frameIntervalMs = max(1, round(1000 / frameRate))
非法帧率
    -> 保留安全默认值33 ms
```

### 5.2 剩余预算计算

```text
intervalNs = scaledIntervalMs * 1,000,000

首次提交：
    deadline = tickStartedNs + intervalNs

后续提交：
    deadline += intervalNs

若deadline落后当前时间超过一个完整间隔：
    deadline = currentNs

remainingNs = deadline - currentNs
delayMs = ceil(max(0, remainingNs) / 1,000,000)
```

使用向上取整避免提前唤醒后反复空转；处理耗时和一般定时器抖动会自然从等待预算中扣除。

## 6. 功能 Phase

### Phase 0：文档与修复边界

- 创建独立架构指导、TODO和Bug报告。
- 固定第一阶段允许修改的文件范围。
- 验收：根因、算法、风险和测试矩阵可追踪。

### Phase 1：调度正确性修复

- 修复120 FPS边界判断。
- 增加单调时钟、绝对截止时间和剩余预算计算。
- 在生命周期与速度切换处重置节奏状态。
- 验收：处理耗时不再叠加到完整帧间隔之后。

### Phase 2：确定性单元测试

- 验证120 FPS得到约8 ms间隔。
- 验证33 ms周期中8 ms处理耗时只剩约25 ms等待预算。
- 验证绝对截止时间能补偿前一轮定时器偏差。
- 验证严重落后时不会形成无界截止时间债务。

### Phase 3：静态验收与运行准入

- 执行文件范围、空白、接口和定向静态检查。
- 用户授权后编译并运行单元测试及30/120 FPS真实素材回归。
- 运行验收未完成前，不宣称真实丢帧率目标已经达成。

## 7. 开发时间估算

| Phase | 预计耗时 | 不确定性 |
|---|---:|---|
| Phase 0 | 0.5小时 | 低 |
| Phase 1 | 1～2小时 | Qt定时器精度、暂停恢复语义 |
| Phase 2 | 1小时 | 测试目标的FFmpeg和Qt链接配置 |
| Phase 3 | 1～2小时 | 真实素材、机器负载和显示刷新率 |

## 8. 最终呈现效果

- 30 FPS视频不再因为约8 ms处理耗时退化到约24 FPS。
- 120 FPS视频不再错误使用33 ms默认间隔。
- 调度器仍可在视频真正落后音频主时钟时主动追帧。
- 暂停恢复、Seek和速度切换后不会沿用旧截止时间。
- UI布局、播放操作和多路渲染行为保持不变。

## 9. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| Windows定时器粒度与事件循环抖动 | 短时FPS波动 | 使用绝对截止时间补偿，不要求每个采样窗口绝对为0丢帧 |
| 处理耗时超过帧间隔 | 120 FPS仍无法全部提交 | 立即追赶并由同步规则丢弃过晚帧，不制造忙等 |
| 多路调度共享UI线程 | 单路负载影响其他流 | 本轮先修复累计等待；线程迁移另立性能专题 |
| 音频时钟包含缓冲提前量 | 同步阈值可能仍触发 | 保留现有20 ms补偿和40 ms阈值，运行验收后再单独评估 |
| 旧的singleShot尚未触发 | 暂停恢复存在残留回调 | `running_`继续作为安全门；定时器代际治理不混入本轮 |

## 10. 运行验收要求

代码完成后至少覆盖：

1. 24/30/60/120 FPS带音频文件，1.0x播放。
2. 30/120 FPS无音频文件。
3. 0.5x、1.5x、2.0x播放速度。
4. 暂停恢复、Seek、停止重播和切源。
5. 单路与30+120 FPS多路混合。
6. 图像处理、视觉分析关闭与开启对照。

默认开发规范只执行静态检查；编译、运行与性能数据采集需用户明确授权。
